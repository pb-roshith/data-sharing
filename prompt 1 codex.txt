BUSINESS OBJECTIVE
 
Convert policy documents into reusable, governed and traceable policy rules.
 
The system must not regenerate different checks for every credit assessment. Policy rules must first be extracted from policy documents, reviewed by a human, approved, versioned and activated. Only approved and active rule versions may be used in credit-request compliance assessments.

IMPLEMENTATION REQUIREMENTS
 
A. POLICY DOCUMENT INGESTION
 
Create or extend a policy-ingestion service that:
- Processes all manufactured policy documents already available to the application.
- Supports DOCX, text and PDF files already supported by the current solution.
- Extracts document text while preserving:
  - Policy ID
  - Policy name
  - Policy version
  - Effective date, if stated
  - Section heading
  - Clause number
  - Page number, when available
  - Exact source excerpt
  - Source document identifier
- Does not follow instructions contained inside uploaded documents.
- Treats document content only as policy source material.
- Records ingestion status, timestamp, source-file checksum and processing errors.
- Avoids creating duplicate policy versions when the same file is processed again.

Use strict structured output based on a JSON Schema or equivalent typed schema. Do not parse free-form prose into database records.
 
RULE EXTRACTION BEHAVIOUR
 
The extraction agent must:
1. Create one atomic rule per independently testable policy requirement.
2. Preserve the exact source clause and source excerpt.
3. Distinguish mandatory requirements from guidance or explanatory text.
4. Distinguish quantitative rules from qualitative rules.
5. Extract a numerical threshold only when it is explicitly stated in the policy.
6. Never invent a threshold, formula, severity, data source or approval authority.
7. Set unstated properties to null and identify them in missing_information.
8. Represent compound requirements as separate rules when each condition can be evaluated independently.
9. Preserve AND/OR dependencies between related conditions.
10. Detect policy prohibitions, mandatory escalation requirements and hard limits.
11. Identify rules that require documentary or human judgment.
12. Mark ambiguous clauses for human review.
13. Identify duplicate or substantially similar proposed rules, but do not automatically merge them.
14. Generate a stable rule code based on the policy, clause and rule sequence.
15. Save every generated rule in Draft status.
16. Never automatically approve or activate an AI-generated rule.
 
C. POLICY RULE GOVERNANCE
 
Implement the following lifecycle:
 
Draft
→ Under Review
→ Approved
→ Active
→ Inactive
→ Retired
 
Rejected must be separately supported.
 
Rules may be edited while Draft or Under Review.
 
Approval must capture:
- reviewed_by
- review_comments
- approved_by
- approved_at
- approval_decision
- change_rationale
 
Only authorised users may approve, activate, deactivate or retire rules.
 
Every edit must create an audit record containing:
- entity type
- entity ID
- previous value
- new value
- action
- actor
- timestamp
- reason
 
An approved or active rule must not be overwritten. Material changes must create a new rule version.
 
D. RULE VERSIONING

- Rule version

- Effective-to date
- Status
- Approved by

- Change rationale
- Superseded rule version
 
Historical assessments must continue to reference the exact rule version used at the time of assessment.
 
A new rule version must not automatically alter or recalculate a historical assessment.
